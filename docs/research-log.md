# Investigation: checkra1n Jailbreak on iPhone 6s (A9, CPID 0x8000)

**Date:** 2026-10-11
**Researcher:** Kali Linux terminal session (root user)
**Status (updated 2026-10-11, 18:50):** deep diagnosis completed - the failure is NOT about size or transfer timing. It is isolated at the USB DFU protocol level: the device correctly completes the entire standard manifest sequence (`dfuMANIFEST-SYNC → dfuMANIFEST → dfuMANIFEST-WAIT-RESET`) and accepts a real USB reset, but after that reset it reappears as the same pwned DFU instead of executing the loaded image. See §19 for the full executive summary of the whole session.

## 1. Goals, Initial Diagnosis, and Resolved Issues (§1–§7)

### §1 Goals and context

Goal: complete the checkra1n jailbreak on my own iPhone 6s. Reported symptom: the exploit reaches "Checkmate!" but stalls at "Right before trigger" or throws `USBMUX Error -79`. Reconnecting the cable doesn't help. Environment: Kali Linux (kernel 7.1.5+kali-amd64), PC with **AMD Rembrandt USB4** USB controllers (xhci_hcd), USB-C ports, native Lightning data cable (no hub or adapter in the final chain). Device: iPhone 6s, iBoot 2234.0.0.3.3.

**Exact DFU serial (ground truth for the device):**

```
CPID:8000  CPRV:20  CPFM:03  SCEP:01  BDID:04
ECID:<ECID>  IBFL:1C  SRTG:[iBoot-2234.0.0.3.3]
```

Chip: **Apple A9 (S8000, Samsung)** - `CPID:8000 CPRV:20`. `BDID:04` = **a less common board variant** (typical 6s/6s Plus/SE use BDID 02/03). iBoot 2234.0.0.3.3 (iOS 13.3 was the era of that iBoot → the device runs iOS ≤13.x, supported by checkra1n). *(Both of these early claims are corrected later - see §9.3.)*

### §2 Problems found and resolved (in order)

**2.1 - Corrupted binary - CAUSE of "stuck at Right Before Trigger" (RESOLVED).** There were two binaries: `~/checkra1n-linux-x86_64` - **554 KB**, self-identifying as "Checkra1n 0.1337.3". **This is NOT the legitimate checkra1n** (the real one is ~10 MB with embedded Pongo images). This binary had been **hung in a loop for 1h36min at 95% CPU** (PID 17126, launched at 12:45), holding the USB device. `~/checkra1n-0.12.4` - **10,360,264 bytes**, "Checkra1n beta 0.12.4" (May 2021 build) - the legitimate one. The corrupted binary was holding the USB, so any subsequent run gave `-79` or hung. Action: `kill -9 17126`. From then on, the exploit became **100% reliable (8/8 runs reach `Checkmate!` + `code execution`)**.

**2.2 - Kernel driver `apple-mfi-fastcharge` (RESOLVED).** The kernel was grabbing the DFU device and competing with checkra1n for interface 0: `usbfs: process 100813 (checkra1n-0.12.) did not claim interface 0 before use`. It re-registered itself on every device re-enumeration. Action: `rmmod apple_mfi_fastcharge` + blacklist in `/etc/modprobe.d/no-apple-mfi.conf`:
```
blacklist apple_mfi_fastcharge
install apple_mfi_fastcharge /bin/false
```

**2.3 - `usbmuxd` - a self-inflicted operational error, corrected (RESOLVED).** Early on, `usbmuxd` was killed/masked by mistake (on the assumption it competed with checkra1n). checkra1n **does** use the system socket (`/var/run/usbmuxd`, strings `Using usbmuxd` and `USBMUXD_SOCKET_ADDRESS` embedded) for the final bootstrap phase. The classic `Error -79` from GitHub issues (#1724, #1551) corresponds to `Using usbmuxd → connection refused` - i.e., usbmuxd absent. Action: unmasked (`rm /etc/systemd/system/usbmuxd.service`), service alive.

**2.4 - USB autosuspend (RESOLVED).** `/sys/module/usbcore/parameters/autosuspend` was set to `2` (the kernel was suspending ports). Action: set to `-1`.

**2.5 - `Error -79` / "Right before trigger" - re-classification.** My original "stuck at Right before trigger" was 100% the corrupted binary (2.1). It was not timing or the cable. My original `Error -79` likely combined: corrupted binary holding the USB + usbmuxd dead during the session.

### §3 The real problem: DFU→boot handoff failure in the BDID:04 variant

**3.1 - Transfer-level evidence (kernel usbfs trace).** `LIBUSB_DEBUG=4` emits nothing (checkra1n's libusb is statically compiled **without debug**), but the kernel traces every failed URB via `usbfs`. All runs (port 3-2 and port 8-1, two different xHCI controllers) show the **same signature**:
```
... Checkmate!
... Trying to run payload...
... If everything went correctly, you should now have code execution.
usb 3-2: usbfs: USBDEVFS_CONTROL failed  rqt 33  rq 4  len 0  ret -71
usb 3-2: USB disconnect, device number 42
usb 3-2: new high-speed USB device number 43   ← re-enumeration
   idVendor=05ac, idProduct=1227               ← DFU again (NEVER Pongo)
usb 3-2: USB disconnect, device number 43     ← 0.75-0.9 s later
```

Decoding the failing transfer:

| Field | Value | Meaning |
|---|---|---|
| `rqt 33` | `0x21` | CLASS, recipient=INTERFACE, direction OUT (host→device) |
| `rq 4` | `0x04` | DFU class request (final phase of the DFU upload protocol) |
| `len 0` | zero-length data stage | the **"execute and reboot"** command (final kick) |
| `ret -71` | `-EPROTO` | the device responds badly / stalls in the status phase |
| `ret -108` | `-ESHUTDOWN` | endpoint shut down: the device is re-initializing mid-transaction |

Conclusion of the transfer analysis: the "send payload" (bulk) does NOT fail. The bulk payload upload **completes** (the log reaches `code execution` and `dmesg` records no bulk URB error). What fails is the **final control transfer (the kick)**: at the instant iBoot restarts to execute the image, the device re-enumerated **as DFU (0x1227) instead of as Pongo USB mode (0x0102)**, and that re-enumeration breaks the in-flight control transfer (EPROTO/ESHUTDOWN).

**3.2 - Test that rules out the rootfs.** Run `checkra1n -p` (boot directly to **Pongo shell**, without uploading a rootfs or installing anything): **failed at the same control transfer, with the same `ret -71`, and the same re-enumeration to DFU**. → The failure does not depend on the rootfs/Cydia/bootstrap: it's the device's DFU→boot transition.

**3.3 - Signs that this is the BDID:04 variant, not the hardware.** 1) **The deterministic run never works:** the log always says `Deterministic approach doesn't seem to work, attempting to do a probabilistic run` / `Entered initial checkm8 state after 16384 steps`. In documented successful runs (issue #1724), `Deterministic approach was successful! ... after 0 steps` appears. This variant's iBoot responds differently from the "golden" A9 the exploit is tuned for. 2) **Identical failure on two ports / two different xHCI controllers** (bus 3-2 and bus 8-1) → rules out a specific port. 3) **Identical failure with a direct native cable** (no hub, no adapter) → rules out the cabling chain. 4) **Public issues with the exact same fingerprint:** dualra1n/dualra1n#93 - iPhone 6s, `CPID:8000 CPRV:20 CPFM:03 SCEP:01 BDID:04 ... iBoot-2234.0.0.3.3`: achieves pwned DFU and uploads the image 100%, then fails at "Unable to connect to device"; in the thread a user reports the same thing ("goes into DFU and then **breaks right before booting**") and the applied fix was: **"this is the one i just added - more sleeps - and it fixed the issue"** → a **timing failure in the handoff** for that variant. axi0mX/ipwndfu#138 - iPhone 6s `CPID:8000 ... BDID:04` reported as unsupported in early versions of the exploit (S8000/N71AP was among the last A9 variants to get support). checkra1n/BugTracker#1568 and #1283 - iPhone 6S with a loop `Checkmate! → code execution → back to DFU → re-exploit` (the same behavior observed here, on a Linux host). checkra1n/BugTracker#1689 (CLOSED, `status-fixed`) - the `Error -79`/`-20` right after a successful checkmate was a known checkra1n bug, fixed in a later release; and in it they confirm that **the iPhone 6s does jailbreak**.

**3.4 - Final diagnosis.**

> checkm8 works 100% on this device (8/8). The payload uploads in full. The failure is **logical/temporal**: when executing the final "kick/reboot" control transfer, the pwned iBoot of the **BDID:04** variant does not switch to Pongo USB mode and **falls back to DFU** ~0.75 s after re-enumerating, interrupting the transfer (EPROTO/ESHUTDOWN). It isn't the cable, the stack, a port, or the rootfs.

### §9 Deep investigation (2026-10-11, afternoon) - findings and corrections

**9.1 - KEY RESULT: the checkm8 exploit works on this host with another tool.** **gaster** (0x7ff/gaster, C + libusb, `make libusb`) was compiled and `gaster pwn` was run against this same iPhone, the same port 3-2, the same cable, the same AMD xHCI controller. Result: **pwned DFU on the first try** → `Now you can boot untrusted images.` and the serial switched to end in `PWND:[checkm8]`. Conclusion: **host, cable, port, AMD controller, and the exploit itself are all valid.** The problem is NOT the PC's hardware; it's specific to the checkra1n 0.12.4 (closed-binary) chain. The "try another host" option loses priority. gaster exposes its timings via environment variables (`USB_TIMEOUT`, `USB_ABORT_TIMEOUT_MIN`, default 5 ms): it's the open, C, adjustable version of the same attack (the "Python → C" idea floated earlier: the bottleneck isn't the language - checkra1n is already native - it's fine control over control-transfer abort timing, which gaster does let you adjust).

**9.2 - Behavior of checkra1n against an already-pwned device.** checkra1n 0.12.4 **does not detect** gaster's `PWND:[checkm8]` and re-exploits anyway ("Exploiting → heap spray → Checkmate! → code execution → Exploiting…"). That re-exploitation of an already-pwned device left it **hung** (`Sanity check transfer failed, device busy or crashed? (-26)`, then `xhci_hcd: Timeout while waiting for setup device command`, `device not accepting address`, error -62/-110): a physical reboot was required. Do not use checkra1n on a device already pwned by gaster. The "Checkmate! → code execution → back to DFU → re-exploit" cycle is **documented by other users**: BugTracker #1568 (6S, iOS 13.2.2, 0.10.2), #1881 (6S, iOS 13, 0.12.1, Debian; "works after 10–20 attempts"), #1065 (iPhone X; maintainer Siguza: "Not a checkra1n issue", the reporter attributed it to the PC's kernel version). None have a confirmed fix from the maintainers; the only reported workaround is to retry.

**9.3 - Corrections to earlier claims in this document.** 1) **"BDID:04 = rare variant"** → probably false. Per the board table (The Apple Wiki, not verifiable here due to a 403) the standard iPhone 6s is N71AP, CPID 8000, **BDID 04**. dualra1n#93's own victim (a normal iPhone 6s) has `BDID:04`. It's not an unusual variant. 2) **"iBoot-2234.0.0.3.3 ⇒ iOS ≤13"** → false. That string is the **SecureROM** of the S8000 and is identical on any iOS version (the dualra1n#93 report is a 6s on iOS 15.8 with the same string). **The phone's iOS version is UNKNOWN** and it matters: checkra1n 0.12.4 officially supports iOS 12.0–14.8.x. 3) **dualra1n#93**: the "fix = more sleeps" was said by a contributor about **a different device (iPad mini 4, A8)** and an unidentified tool; the iPhone 6s report was closed without an explicit fix. It is not direct evidence of a BDID:04 timing bug. 4) **"No hub" as a dismissal**: per ElcomSoft/LukeZGD, a hub is actually a **documented workaround** for 6s/SE on certain hosts, not a cause. And **AMD** controllers are listed as less reliable for checkm8 (LukeZGD Legacy-iOS-Kit wiki), although here gaster proved it works. 5) Route B (patching PongoOS) is still ruled out: the failure happens before Pongo.

**9.4 - Working hypotheses (ranked).** **H1 (most likely)**: checkra1n's exploit doesn't actually manage to pwn the device (the "Checkmate!" prints after the trigger, but `PWND:` is never verified); the reset to DFU we see is a heap crash/failure, not a successful handoff. Evidence: identical cycle in public reports; the deterministic run never works (16384 steps); no capture exists of the serial showing `PWND` after a checkra1n run. → **Experiment A** (`~/cr1-experimento.sh` script): run checkra1n against a fresh DFU with a USB sampler at 30 ms and see if `PWND:[…]` appears after the kick. **H2**: checkra1n does pwn but its next stage (uploading Pongo) fails due to xHCI timing on this very recent kernel (7.1.5; #1065 suggests kernel sensitivity). **H3**: the phone's iOS is > 14.8 (unsupported by 0.12.4) → KPF/boot would fail *later*; doesn't explain the earlier failure but worth confirming.

**9.5 - Proposed solution depending on Experiment A's outcome.** If **PWND does NOT appear after the kick** (H1): checkra1n isn't viable on this host/kernel. Alternative: pwn with **gaster** (works) + load Pongo/boot with a custom pipeline (PongoOS needs `ld64`+`cctools-strip` to build; not installed on this PC; `irecovery`/`img4tool` aren't either). This is real engineering work (like the pomme/a9boot projects), with no guarantee. If **PWND appears and it fails afterward** (H2): try an older LTS kernel / another xHCI controller (a PCIe USB card, recommended by LukeZGD for AMD hosts) / a hub. Either way: confirm the iOS version (Settings → General → About) before investing further.

### §10 Experiment A results (2026-10-11 16:34) - H1 CONFIRMED

Evidence folder: `~/cr1-exp-163408/` (cr1.log, sampler.txt, dmesg-delta.txt).

USB timeline (30 ms sampling) during a checkra1n run against a fresh DFU:
```
 0.05s  3-2 pid=1227 dev=58  (no PWND)      ← clean DFU
13.05s  (absent)                            ← trigger fires: the device RESETS
14.57s  3-2 pid=1227 dev=60  (no PWND)      ← comes back as CLEAN DFU (no PWND)
14.64s  (absent)                            ← vanishes from the bus and never returns
```
dmesg: `USB disconnect, device 58` **before** the control transfer fails (`rqt 33 rq 4 ... ret -108`), then two DFU re-enumerations (dev 59 and 60) **without `PWND:[...]`**, then total disappearance.

Conclusion: checkra1n's "Checkmate!" **does not imply a pwn**: the trigger **hangs/resets the SecureROM** and the device goes back to a clean DFU (never with `PWND`). The `ret -71/-108` of the kick is a consequence (the device had already reset), not the cause. Same host, same port, same cable: **gaster does pwn** (`PWND:[checkm8]`). The difference is in how checkra1n 0.12.4 runs the heap-spray/trigger (deterministic run fails → falls back to the 16384-step probabilistic one) versus gaster's abort-timeout scheme. §3.3/§3.4 (the "BDID:04 handoff" diagnosis) are now **superseded**: the failure isn't the post-exploit handoff, it's that checkra1n's exploit never manages to pwn on this host.

**Options, from least to most effort:** 1) **USB 2.0 hub** between PC and cable (a documented workaround for 6s/SE; changes how control-transfer abort/cancel is handled). 10 min. 2) **A different kernel/xHCI stack**: a live USB with an older kernel (Ubuntu 22.04/Debian 12), or a PCIe USB card (recommended for AMD hosts). 20–30 min. 3) **Another host** (Intel / macOS) just for pwn+boot with checkra1n. 4) **Hybrid gaster→custom boot**: pwn with gaster (proven) + a custom Pongo boot chain. There's no verified tool for A9 on Linux (pomme/a9boot are experimental and "untested on hardware"). An engineering project, no guarantee. Still pending: **the phone's iOS version** (if > 14.8.x, checkra1n 0.12.4 isn't the right tool; it would be palera1n, which also depends on checkra1n's exploit).

### §11 Continuation (2026-10-11, 16:50) - gaster reviewed, automatic retrying

**11.1 - `gaster` (0x7ff/gaster) cloned and reviewed - confirms explicit device support.** The source code (`gaster.c`) has a table of hardcoded addresses keyed by `SRTG`, and **`SRTG:[iBoot-2234.0.0.3.3]` is explicitly supported** (not a generic fallback), with `boot_tramp_end`, `dfu_handle_bus_reset`, etc. specific to this exact iBoot build. This independently confirms that this iPhone 6s's device/iBoot is a known, supported target of the checkm8 exploit - nothing is atypical about the hardware. **Limitation of this gaster version**: its CLI only exposes `pwn | reset | decrypt | decrypt_kbag`. There's no command to upload Pongo/execute an arbitrary image after the pwn - its own post-pwn payload is tiny (patching checks, reading the KBAG, demote), not an OS loader. Reimplementing the DFU→Pongo handoff by hand would amount to rebuilding checkra1n's closed-source part with no guarantee, so that path is set aside for now (see §11.4 if revisited).

**11.2 - Experiment: automatic checkra1n retries without manually re-entering DFU.** Hypothesis: since in Experiment A the device bounced twice as a clean DFU after the failure before disappearing, maybe several `checkra1n -p` attempts could be chained without touching the phone. **Result of attempt 1** (script `cr1-retry/retry.sh`): reached `Checkmate!` + `code execution` as always, but this time the device **disappeared from the bus entirely** (no DFU, no Pongo, nothing in `lsusb`) and never reappeared after several seconds of polling. **Conclusion**: the post-failure behavior isn't 100% repeatable bounce-to-bounce (sometimes it returns to clean DFU 1-2 times, other times the iBoot/SecureROM ends up in a state that drops the USB line entirely) → **re-entering DFU does sometimes require the physical button combo**. This is **not evidence that the problem is physical** (the failure is still the same one as always: the trigger doesn't leave the device pwned); it's simply that *recovering* from a failed attempt sometimes requires a physical action only the person holding the phone can do.

**11.3 - Process fix: background supervisor.** To avoid spending every manual DFU reinsertion on a single attempt, `cr1-retry/supervisor.sh` was left running: it watches the USB bus, and as soon as it detects `05ac:1227` it automatically relaunches a burst of `checkra1n -p` (sampling `iSerial` for `PWND:[checkm8]`) until the device drops off the bus again - maximizing the number of attempts per manual DFU reinsertion. It stops on its own (via a `SUCCESS` file) if any attempt does leave the `PWND:[checkm8]` string, or after 50 cycles, or if a `STOP` file appears. Status: running in the background, waiting for the phone to reappear in DFU.

**11.4 - Pending human action.** **I need to put the iPhone back into DFU mode** (physical button combo) so the supervisor can keep testing. This is a mechanical recovery step, not an admission that the root cause is hardware.

**11.5 - Supervisor fix + new finding: the phone boots clean after the failure.** **Bug found and fixed**: the first version of the supervisor detected "device present" with `lsusb -d 05ac:` (any Apple product), so when the phone finished booting to **normal iOS** (`idProduct 0x12a8`, with `iSerial` = real UDID, not the CPID/BDID DFU string) after a failed attempt, the supervisor kept uselessly launching `checkra1n -p` against it. Fixed to specifically require `05ac:1227` (DFU) on each check. **New important data point**: after session 1's failed attempt (two sub-attempts, neither with `PWND`), the phone **booted cleanly into normal iOS** (it didn't get stuck, didn't end up in a broken state) - further confirmation that there's no physical/firmware damage: the device boots perfectly on its own when left alone; the only thing that fails is specifically the checkra1n trigger within the DFU window. Supervisor relaunched (fixed version) and it already detected a new real DFU session underway.

## 3. Switching to gaster + Direct DFU Upload (§12–§17)

### §12 Continuation (2026-10-11, 17:17) - gaster + direct DFU, bypassing checkra1n's exploit entirely

**12.1 - Strategy change (prompted by my own question: "do we really need that many [attempts]?").** checkra1n: 0/6 real, its own exploit unreliable on this host (never deterministic, always the 16384-step probabilistic path). gaster: **1/1 reliable** again (as in §9.1) - `gaster pwn` left the serial at `PWND:[checkm8]` on the first try. `checkra1n --help` has no option to "skip the exploit and continue on an already-pwned device" (only `-k/--override-pongo` to change WHICH Pongo is uploaded, not HOW the pwn happens). Combining it with gaster isn't viable (confirmed in §9.2: it re-exploits and hangs the device). **Result - the device does follow the standard DFU protocol to the letter:**
```
GET_STATUS poll 0 -> state=6   (dfuMANIFEST-SYNC)
GET_STATUS poll 1 -> state=7   (dfuMANIFEST)
GET_STATUS poll 2 -> state=8   (dfuMANIFEST-WAIT-RESET)
GET_STATUS poll 3..5 -> state=8  (stable, waiting)
```
This is the **correct, expected** sequence of the DFU standard (USB DFU 1.1 §9.2.6, states `dfuMANIFEST-SYNC → dfuMANIFEST → dfuMANIFEST-WAIT-RESET`) - the device confirms it accepted the image and that, per protocol, it's now the host's turn to issue a **USB reset** so the device relaunches and executes the loaded image.

**Exactly that was tested** (`irecv_reset()` on the same open handle, without closing/reopening the connection, to avoid losing state): `irecv_reset()` returned success, and `dmesg` confirms that **a real port-level USB reset did happen** (`reset high-speed USB device number 103 using xhci_hcd`, matching timestamp). But after that reset, the device **settles back as the same old pwned DFU** (`05ac:1227`, `PWND:[checkm8]`) - never as `05ac:4141` (Pongo).

**This pins down the failure with millimeter precision:** the standard DFU protocol is honored from start to finish (manifest, states, reset) - this is not a timing problem in the sense suspected in §3 (no control transfer fails, no `EPROTO`/`ESHUTDOWN`; everything responds `OK`). The USB reset really executes (confirmed by the kernel). And even so, the iBoot patched by *gaster* does not execute the image after that reset - it simply relaunches the same pwned DFU responder. This points to gaster's patch to `dfu_handle_request` (which is only designed to let its **own** exploitation payload through, not to serve as a generic DFU loader for arbitrary images) probably not correctly re-arming, for this `SRTG:[iBoot-2234.0.0.3.3]`/`CPID:8000`/`BDID:04` combination, the jump path that Apple's standard DFU normally activates on reaching `dfuMANIFEST-WAIT-RESET`. In other words: the "kick" doesn't fail from misuse of the `libirecovery` API (tested manually at a low level, bypassing `libirecovery` almost entirely) - it's gaster's own patch that, apparently, doesn't let iBoot complete that final jump for data other than its own internal payload.

## 5. Pointer-Slot Model and the Real SecureROM/Boot Addresses (§18–§20)

### §18 Continuation (2026-10-11, ~19:00) - verifying the jump encoding, correcting the model (pointer slot), and the first test artifact

**18.1 - Encoding verified with a real assembler.** Assembled with `aarch64-linux-gnu-as` (checkra1n's binary plays no part here; an independent check):
```
movz x0, #1, lsl #32   ->  d2c00020
br   x0                ->  d61f0000
```
8-byte sequence (little-endian), as it would sit in memory:
```
20 00 C0 D2 00 00 1F D6      (u64 = 0xD61F0000D2C00020)
```
A no-clobber-x0 variant (in case it's needed): `movz x16, #1, lsl #32; br x16` = `30 00 C0 D2 00 02 1F D6` (u64 = 0xD61F0200D2C00030). Cross-check: `aarch64-linux-gnu-objdump -d` disassembles `d2c00020` as `mov x0, #0x100000000` and `d61f0000` as `br x0`. The encoding **is correct**; the problem is where it was planned to be written (18.2).

**18.2 - CORRECTION: `dfu_handle_bus_reset` is not code - it's an 8-byte pointer slot in the SecureROM's USB/DFU state.** Direct evidence from gaster's source (where the idea originally came from): `payload_A9.S` does `ldr x2, =dfu_handle_bus_reset; str xzr, [x2]` - i.e. it **stores a u64 (zero) AT address 0x180087928**. If it were code, `str xzr` would write 8 zero bytes (= `udf` x2), not a "null pointer". The value loaded by that `ldr` comes from the payload's **literal pool**, which in the compiled payload (`payload_A9.bin`, 280 bytes) is the last 104 bytes - the `struct A9` template that the **host** fills in with real addresses before sending it (`payload_sz = payload_A9_bin_len - sizeof(A9)`; the host appends its own struct right where the code expects its literals). The struct's fields: `pwnd[2], payload_dest, dfu_handle_bus_reset, dfu_handle_request, payload_off, payload_sz, memcpy_addr, ...` - fixed 8-byte positions. The **neighboring** slot `dfu_handle_request` (0x1800878F8) receives `str x1, [x2]` with `x1 = payload_dest+0xC` - a **code pointer**. In other words, 0x1800878F8/0x180087928 hold pointers to functions of the SecureROM's USB/DFU dispatcher (a data region in SRAM, `0x18008xxxx`), while the SecureROM's code lives at `0x1000xxxx` (`handle_interface_request = 0x10000F1B0`, `usb_core_do_transfer = 0x10000EE78`, `memcpy_addr = 0x100011030`) - ipwndfu's standard DFU chain (`usbexec.py`) uses the **same slot-based model**. Consequence: writing `movz x0,#1,lsl#32; br x0` (8 bytes of **code**) there would leave the slot holding the garbage-pointer `0xD61F0000D2C00020`: if the SecureROM calls that handler, it jumps to a wild address (a crash), not to 0x100000000. To hook our own code into that event, we need to write **the address of our stub** (a u64), not instructions. Additional layout note: in `payload_A9.bin`, the string `" PWND:[checkm8]"` (16 B) needs to sit **exactly** at the start of the last `sizeof(A9)` = 104 bytes, because the host overwrites from there with its struct (the first word of this IS the pwnd field, and the literal pool starts at +0x10). Any payload change that shifts that string by 4 bytes silently breaks the contract (corrupting the PWND string). See 18.5 for how to patch without breaking it.

**18.3 - CORRECTION: 0x100000000 is not a load address - it's the SecureROM's base and Pongo's link (VA) address.** `ipwndfu/device_platform.py`: `rom_base = 0x100000000` for all supported arm64 SoCs (A7 onward). This is the **address of the SecureROM's ROM code** (confirmed on this very device: gaster patches the signature check at `patch_addr = 0x10000812C`, i.e. ROM+0x812C). The **real DFU load address** is `dfu_image_base` (= `insecure_memory_base` in gaster = **0x180380000** in SRAM for our iBoot 2234; in device_platform.py: A7 `0x180380000`). This is where DNLOADs land and where gaster reads its `EXEC/MEMC` command block after `dfu_send_data` - and therefore where our Pongo image landed (100% transferred) in §16/§17. `-Wl,-image_base,0x100000000` in PongoOS's Makefile is **only the link base (layout offset)**. The flat image is position-independent: `src/boot/entry.S` (`start`) copies 2 MB of itself to **0x818000000** (`movz x5,#8,lsl#32; movk x5,#0x1800,lsl#16`) using `adr` (PC-relative, works at any load address) and continues running there; `src/kernel/mm.c` then maps `VA 0x100000000 -> pongo_base` (the real physical address) and defines `gPongoSlide = 0x100000000 - pongo_base`. In other words: the image never runs "at" 0x100000000; VA 0x100000000 is *where Pongo maps itself* AFTER its trampoline runs. `src/boot/entry.S` + `stage3.c` further document Pongo's real entry contract when launched by a bootloader: branch via `br x27` or `br x29` with `x8 = boot_image` and `x0 = boot_args` (→ `trampoline_entry(boot_image, boot_args)`; with `boot_args == NULL` it enters "bootloader/KJC" patching mode, and with `boot_args != NULL` it runs Pongo's `main()`). A bare `br` with arbitrary registers is NOT a valid Pongo boot.

**18.4 - New hardware finding: the handler slots get re-initialized on every re-enumeration.** The read primitive of the 0xA1/2 protocol (the same one ipwndfu's `usbexec` uses: a DNLOAD of a `MEMC_MAGIC` block, reading back the response = data copied to 0x180380000) was tried against the **already-pwned** device still connected (`PWND:[checkm8]` in the iSerial, `lsusb 05ac:1227`). First try with `libirecovery` (irecv_usb_control_transfer) → failure `-7` (USB status). Second try replicating gaster's exact flow by hand with libusb (open + `libusb_set_configuration(1)` + DNLOAD in 0x800 chunks + request 0xA1/2 wValue=0xFFFF) → also a `-7` timeout, even adding `usbexec`'s exact prologue (16 zero bytes + zero-length DNLOAD + 2×GET_STATUS). Slots at `0x40..0x4F` get wiped *between commands* (only safe intra-command). 2) **The EXEC block**: `[0]magic, [8]func, [0x10..0x4F]args`; the shim reads x6/x7 from 0x40/0x48 (read-only). **Always send it explicitly**; a `ret=16` with no block sent = a silent fallback (magic=0) → a false positive (the §29.3 `pongo_boot3` bug). 3) **Always print the response's contents** (DONE magic + retval), not just `ret`. 4) **Stub literal offsets**: patch them at the right position (`+16` for stub4; `+48→+52→+64` depending on the preamble; each tool's helper fixes it). 5) **Layout overlaps** when placing stubs in the blob (M4/stub5, T4/stub5 → phantom hangs). Space them ≥0x80 beyond the largest one. 6) **EL3**: `mrs/msr` of EL1 registers (`ttbr0_el1`, `sctlr_el1`, …) are ILLEGAL in EL3 (the SecureROM runs in EL3); `spsel` is legal. Save the EL1 world only from code already running in EL1. 7) **Probe depth**: better passed via the EXEC block's x0 argument (the stub copies it to the slot) than via MEMC (visibility not guaranteed). 8) **Pattern verification**: objdump shows `movz` as `mov`; byte patterns must be computed carefully (Rd in the low byte). 9) **Don't use `gaster-force`** (re-exploit loop → an inconsistent device); a physical restart is the clean recovery. 10) **Pongo's stock entry assumes EL3 without initializing SP_EL1** (§29.1) - don't follow the stock flow blindly.

**33.3 - The real boot architecture (decoded from jbinit's code - `github.com/palera1n/jbinit`).** The kernel boots the REAL root; then **fakedyld** (from `/cores`) runs as launchd's dyld and, in `mountroot()`, **remounts `/` onto the fakefs** (`mount("apfs","/",…,{rootdev})` with a retry loop; for setup boots it uses the realfs derived from the rootdev by replacing the last digit with `1`). Afterward `prepare_rootfs()` bind-mounts (read-only bindfs) each real directory onto its target in the fakefs (the `fbi` macro, §33.2.3). The payload (`prelaunchd`) mounts the binpack/loader and, if setup flags are set, runs `setup_fakefs()` (fsck+mount phases+init_data_protection → a space check (full only) → APFSVolumeCreate → a copy with a skip-list → the `orig-fs` snapshot → nvram → auto-boot=false). `load_etc_rc_d`: the rootful's `/etc/rc.d` scripts run after the pivot (our boot-loggers there weren't running because the fakefs was never root yet - a phase since superseded).
